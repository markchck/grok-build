# 집필 규격 (모든 장 공통)

이 문서는 각 장을 집필하는 사람(또는 에이전트)이 반드시 따라야 하는 형식 규격이다.
커리큘럼 전체 설계는 `docs/00-curriculum.md`를 본다.

## 독자
Python, FastAPI, 문서 처리, Milvus, OpenAI 호환 모델 서버를 다뤄본 개발자.
목표는 LLM 애플리케이션과 에이전트 프레임워크의 원리를 단계적으로 이해하고 직접 구현하는 것이다.

## 언어와 용어
- 한국어로 설명한다.
- 전문 용어는 처음 등장할 때 의미를 풀어 쓴다. (예: "청킹(chunking, 긴 문서를 검색 단위로 자르는 작업)")
- 영문 고유명사(FastAPI, Milvus, LangGraph 등)는 그대로 쓴다.

## 장별 절 구성 (순서 고정)
각 장은 아래 8개 절을 이 순서대로 포함한다.

1. **학습 목표와 완성 모습** — 이번 장에서 만들 기능, 배울 개념, 실제 동작 예시. 앞 장의 어느 부분을 확장하는지 명시.
2. **핵심 개념** — 무엇인지, 왜 필요한지, 어떤 주체(모델 / 애플리케이션 / 프레임워크 / 도구 서버 / 관측 플랫폼)가 실행하는지. 비슷한 개념의 차이와 사용 조건. 필요하면 흐름도(코드블록 ASCII) 또는 비교표.
3. **실습 준비** — 패키지와 버전, 환경 변수, 폴더 구조, 샘플 데이터, 실행 조건. 실제 비밀키는 절대 쓰지 않고 `sk-xxxx` 형태의 예시만 쓴다.
4. **단계별 구현** — 작은 단위로 코드를 제시하고 각 코드의 역할을 설명한다. **코드 블록마다 파일 경로를 바로 위에 명시**한다. 핵심 실행 코드를 생략하거나 의사 코드만으로 완료 처리하지 않는다. 최소 예제 → 누적 프로젝트 적용 순서.
5. **실행과 결과 확인** — 실행 명령, 요청 예시, 예상 출력, 정상 여부 확인 방법. 모델 출력 문구는 달라질 수 있으므로 구조와 동작 중심으로 확인한다.
6. **실패 상황 실습** — 대표 오류를 의도적으로 발생시켜 원인과 해결 과정을 보여준다. 해당 단계에 필요한 오류만 다루고 과도한 운영 구성을 먼저 도입하지 않는다.
7. **응용 과제** — 학습자가 도구나 검색 조건 등을 바꿔보는 작은 과제. 완료 기준과 힌트 포함.
8. **핵심 정리와 확인 질문** — 핵심 개념 요약, 자기 말로 설명할 수 있는지 확인하는 질문, 이 장의 완성 코드 위치, 다음 장 연결점.

## 정확성 규칙 (예외 없음)
- **실제로 실행해 검증하지 않은 코드를 "검증했다"고 쓰지 않는다.** 각 장 맨 아래에 검증 상태를 명시한다.
  예: `> 검증 상태: 본 장의 코드는 문법 검사만 수행했으며 실제 모델 서버 대상 실행 검증은 하지 않았다.`
- API 시그니처, 패키지 이름, 파라미터는 최신 공식 문서로 확인하고 **출처 URL을 각 장 하단 "참고 문서"에 남긴다.**
- 확인하지 못한 항목은 `[확인 필요: ...]`로 표시한다. 그럴듯한 값을 지어내지 않는다.
- 버전은 "이 문서 작성 시점 기준 x.y" 형태로 쓰고, 상위 호환을 단정하지 않는다.
- **모든 OpenAI 호환 서버가 도구 호출·구조화 출력·스트리밍을 동일하게 지원한다고 가정하지 않는다.** 해당 기능을 처음 쓰는 장에서는 "서버가 이 기능을 지원하는지 먼저 확인하는 방법"을 함께 제시한다.
- **LangChain이 모든 기술의 기반이라고 설명하지 않는다.** 프레임워크는 선택지 중 하나로 다룬다.
- 라이브러리 이름만 나열하지 않는다. 모델 / 애플리케이션 / 프레임워크 / 도구 서버 / 관측 플랫폼 각각의 책임을 구분해 설명한다.

## 용어 해석 (사용자 합의 사항)
- "thinking 과정 표시"는 **모델 내부 사고 원문 노출이 아니다.** 실제 실행 이벤트, 도구 호출, 작업 계획, 상태, 짧은 판단 요약을 보여주는 것이다. 내부 추론을 재현했다고 주장하거나 가짜 사고 과정을 만들지 않는다.
- "Agent-to-Agent"는 내부 하위 에이전트 협업과 별도 A2A 프로토콜을 **구분해서** 다룬다.
- 사용자가 쓴 `middlestream`은 미들웨어와 스트리밍을 뜻하는 것으로 해석해 둘 다 포함한다. 정식 용어로 취급하지 않는다.

## 누적 프로젝트
전 장이 하나의 문서 분석 프로젝트에 기능을 누적한다. 새 개념은 작은 독립 예제로 익힌 뒤 프로젝트에 적용한다.
각 단계의 완성 코드를 `code/stepNN_*/` 아래에 제공해 앞 단계에서 막혀도 이어갈 수 있게 한다.

기본 구현 방향: Python + FastAPI, 단순한 웹 UI, Milvus, OpenAI 호환 모델 서버.

## 파일 규칙
- 장 본문: `docs/NN-제목.md` (NN은 01~13)
- 완성 코드: `code/stepNN_슬러그/`
- 각 장 본문에서 코드 경로를 언급할 때는 리포지토리 루트(`ai/llm-agent-tutorial/`) 기준 상대 경로를 쓴다.

## 문체
- "~한다" 평서체로 서술한다. 문서 전체 종결어미를 통일한다.
- 공허한 연결구를 쓰지 않는다: "결론적으로", "핵심은 ~라는 것입니다", "주목할 점은", "~라는 점에서".
- 이중 완화 표현을 쓰지 않는다. ("~것으로 보이는 부분이 있을 수 있다" → "~부분이 있다")
- "구조"라는 단어를 남용하지 않는다.
